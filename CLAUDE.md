# CLAUDE.md — Ohio Voter Registration Parser

## 1. Project Overview
Ohio Statewide Voter File (SWVF) parser and precinct-captain dashboard. Ingests raw county data to generate deterministic, cohort-segmented voter rosters and jurisdictional narratives. **Task status lives in Linear** (§1a); **domain decisions and rationale** live in the agent memory systems (auto-loaded via `MEMORY.md`), not here and not in the repo. Those memory stores are external and environment-specific: Claude Code CLI reads `~/.claude/projects/D--vibe-election-data/memory/`; Cowork reads its own space memory. This file holds only universally applicable rules and irreducible domain semantics.

## 1a. Task tracking (Linear)
Task/work state is tracked in **Linear**, workspace team **Doorstep Democracy** (issue key `DOO`), via the Linear MCP connector. Two-layer convention (adopted 2026-07-27):
* **Linear = status.** Each unit of work is an issue (`DOO-N`) in a subsystem **project** (e.g. `Trajectory / Axis A — subscriber tier`, `Captain / Quorum App`, `Weekly Change Engine`, `Precincts`). Status/priority/blocking-relations live in Linear fields, never duplicated in prose.
* **Handoff files = spec.** Each issue links a self-contained `local/context/handoffs/HANDOFF_*.md` — the thing a fresh session actually executes. A long spec never goes in an issue description.
* **Runbook files = index.** `RUNBOOK_*.md` point at the Linear project and hold rationale/consistency-checks/scope, not live status.
* **Commits reference the issue.** Every commit message (merge commits included) ends with `Refs DOO-N.` naming the issue it serves; if none applies, ask before committing.

**Fresh-session entry point:** the user names a `DOO-N`; `get_issue` it, follow its `Handoff:` path, execute the handoff, and move the issue In Progress → In Review. If the handoff is marked "TO BE WRITTEN," write it (modeled on an existing handoff) and stop for review before executing — writing and executing a handoff are separate sessions. Detail: memory `project-linear-migration`.

## 4. SWVF Schema & Domain Semantics
The irreducible knowledge this file exists to hold — most of the project's worst bugs were schema misunderstandings, not code defects.

**Source files.** 4 split flat files (`SWVF_1_22.txt`, `SWVF_23_44.txt`, `SWVF_45_66.txt`, `SWVF_67_88.txt`). Comma-delimited **CSV**, double-quoted fields, UTF-8 — despite the `.txt` extension. NOT pipe-delimited. 46 static cols + 89 dynamic election cols. Official layout: local/source/Voter_File_Layout.md

**Join keys.** `SOS_VOTERID` is the statewide key. `COUNTY_ID` is county-scoped — never join on it across counties.

**Jurisdiction columns vs. postal address.** `CITY`, `VILLAGE`, `WARD`, `TOWNSHIP` are authoritative jurisdiction fields. `RESIDENTIAL_CITY` is the USPS mail-delivery city — postal, **not** a jurisdiction. Never assign municipal jurisdiction from `RESIDENTIAL_CITY`, and never treat `PRECINCT_NAME` as a jurisdictional proxy (precincts are named for physical boundaries, not the voter's municipality). City-resolution hierarchy: `CITY` → `VILLAGE` → `WARD` prefix → `TOWNSHIP` (means "not a city" → emit `None`) → `RESIDENTIAL_CITY` (true last resort, ~1 county). A `PRECINCT_NAME` township token (`TWP`/`TOWNSHIP`/trailing `" TS"`) outranks a minority village value. Conflating postal with jurisdiction mislabeled 56% of precinct pairs and went undetected for weeks.

**County-scoped jurisdiction types.** `TOWNSHIP`, `VILLAGE`, `MUNICIPAL_COURT_DISTRICT` collide on name across counties (Washington Township in 23 counties; BELLEVUE municipal court in 3). Aggregate on the composite key `(COUNTY_NUMBER, name)`; `county_scoped: True` in `jurisdictional_groupings.py` triggers the slug/display convention.

**Ward entities are municipality-scoped, not globally unique.** Ward *names* are neither globally unique — 16 raw `WARD` values collide across counties (five distinct `"FIRST WARD"`s, four `"WARD 1"`s, etc., 2026-07-09 measurement) — nor reliably city-prefixed (`"FIRST WARD"`, `"WEST WARD"` carry no municipality token). A bare `(COUNTY_NUMBER, name)` key would therefore either split one real cross-county ward (Alliance's `WARD 2` spans Mahoning + Stark as one city ward) or silently merge unrelated municipalities (five different `"FIRST WARD"`s). Canonical ward entities are keyed `(parent_place, ward_value)`, where parent_place is the **dominant resolved place** among the ward's voter rows — never parsed from the ward string. The single ward resolver is `voter_data_cleaner._ward_map_per_county`; `jurisdictional_groupings.build_ward_entities` and the precinct-index `ward_slug` stamp both derive from it, so a stamped ward can never point to a non-existent entity. **Townships have no wards** — any `WARD` value whose dominant resolved parent is a township is schema abuse, not a ward (Lucas stuffs `"WASHINGTON TOWNSHIP"`/`"WATERVILLE TOWNSHIP"` into `WARD`; Stark's `WARD="CANTON"` tags 8,182 township voters, distinct from Canton City's real wards) — excluded statewide, tracked in `DATA_QUALITY.md`. **Ward coverage is a state-data property, not derivable**: some counties populate `WARD` for a city's voters while another county sharing that same city (e.g. Kettering spanning Montgomery + Greene) does not — never impute the gap; flag it (`tools/admin/validate_jurisdiction_fields.py` §[6]).

**Tree-node totals vs. entity/hero totals — both correct, different scopes.** A geo-tree node sums only the precincts whose *dominant* place assignment is that node (one-precinct-one-node); a jurisdiction's own stats page (hero number) is row-accurate, summed directly from every voter row carrying that jurisdiction, including straddling precincts assigned elsewhere in the tree. For a jurisdiction split across precincts (e.g. Washington Township, Montgomery Co.), the tree node (29,154, its 29 dominant precincts) and the hero (48,657, every voter with `TOWNSHIP=WASHINGTON TOWNSHIP` across 47 precincts) are both correct — they answer different questions ("which precincts does this node own" vs. "how many voters actually live in this jurisdiction"). Do not "fix" the discrepancy.

**Status / affiliation semantics (Ohio EOM Ch.15).** `REGISTRATION_DATE` is never reassigned on name/address change, but it **does** reset on cancellation + reactivation — so it is a first-registration proxy for most voters and *wrong for a measurable minority*: **10.9% of Montgomery voters (39,234) have ballot history predating their registration date, median 9.5 years earlier** (measured 2026-07-24, snapshot 07-04). Never use it alone as an "eligible from" anchor; use `min(REGISTRATION_DATE, first observed ballot)` — a cast ballot proves registration was active. `VOTER_STATUS` is `ACTIVE` or `CONFIRMATION` only (collapses 6+ internal substatus codes; subtype needs county files).

`PARTY_AFFILIATION` is `R`/`D`/empty **plus a minor-party tail** (`L` Libertarian 11,903 and `N` 1 statewide, 2026-10-24, in all 88 counties). Never branch on R/D/empty alone: those voters fell through the cohort ladder and every party chart dropped them for months (cohort `MINOR_PARTY` now; `DATA_QUALITY.md` PARTY-AFFILIATION-MINOR-PARTY). It is behavior-derived: per **R.C. 3513.19** it is the **most recent** partisan primary ballot within the **current calendar year plus the previous two** (EOM "PARTY AFFILIATION"). Three consequences: (1) it is *most recent*, not *any* — a D-2024/R-2026 voter is `R`, so it is NOT a history summary; use the election-history columns as ground truth. (2) The window is **calendar-year bounded, not a rolling 24 months** — it steps on January 1, dropping a whole year at once, and boards refresh after each primary. (3) It is therefore **a function of the snapshot, not of the voter**: across snapshots voters change affiliation with zero behavior change, purely by aging out. Two snapshots are comparable on affiliation only if their windows match — the window is stamped into the enriched-cache provenance (`affiliation_window_years`) so this is testable rather than remembered.

**Election history (dynamic cols — the count GROWS with each election; 91 in the 2026-07-04 snapshot: 46 PRIMARY / 31 GENERAL / 14 SPECIAL, range 03/07/2000 → 06/23/2026).** Never hardcode the count or the end date — resolve the set with `identify_election_cols()` (regex-driven) and its metadata with `build_col_meta()`. Header format `[TYPE]-[MM/DD/YYYY]`, TYPE ∈ {`PRIMARY`, `GENERAL`, `SPECIAL`}. The date lives in the column **name**; the cell holds `R`/`D` (party primary ballot), `X` (non-partisan), a minor-party code (`L`/`G`/`C`/`S`/`N`/`E`, a real party ballot, counted in `m_primaries`, not `x_primaries`), or empty (didn't vote). 2 calendar years of blanks → supplemental list maintenance → `CONFIRMATION`.

**Blank cells are empty strings, not null.** SWVF arrives with `""`, not `null`; null-aware ops (e.g. `pl.coalesce`) skip nothing. `.replace("", None)` before coalescing or filtering on nullity.

**Derived columns.** Legacy `PascalCase` temporals: `Generation`, `Decade`, `BIRTHYEAR` — current code emits these verbatim, so match them exactly (it is `BIRTHYEAR`, not `birth_year`). They are a pending migration target; all *new* derived columns use `snake_case` per §6, and the doc flips these only *with* the code that renames them. Canonical `Generation` values are exactly `Silent/Greatest`, `Baby Boomers`, `Gen X`, `Millennials`, `Gen Z` — not Pew shorthand; wrong labels silently return 0 rows.

**Not in SWVF.** Last Activity Type, ballot method (`_TYPE` absentee/Eday/provisional cols), CONFIRMATION subtype — county files only. Precinct canvass (P3+): https://www.ohiosos.gov/elections/election-results-and-data/

## 5. Data Processing Principles
* **The 88-county assumption (heterogeneity-until-proven-uniform) — the law the rest of this section serves.** The SWVF (and every stream after it: elected officials, results, committees, maps) is not one dataset. It is 88 sovereign Boards of Elections, managed by a handful of vendors, each with its own data-entry habits, formats, missing columns, and schema abuse — concatenated under one fixed SoS schema that normalizes *columns but not meaning*, and all of it drifts over time. **A source column's meaning is therefore heterogeneous across counties until a bounded profile proves it uniform. Cross-county uniformity is the claim that must be earned, never the default.** Before any code branches on, aggregates, or resolves a source column, one of two things must be true: (a) a bounded per-county profile (`value_counts()` / `COUNT(*)` / null-rate by `COUNTY_NUMBER`) exists proving the column means the same thing everywhere the code uses it — cite it; or (b) the code treats divergence as expected (behavior-keyed, not county-keyed). Divergence spans four levels — **value** (same column, different meaning: `WARD="CANTON"` = township, not a ward), **schema** (column present here, absent there), **format** (the concept arrives as CSV here, PDF/HTML/zip there — there may be no column to profile), **provenance** (which artifact is authoritative is itself unknown: `electedofficials (1).csv`, empty `-test.json`). Every known deviation is ledgered in `DATA_QUALITY.md` (the heterogeneity registry, §7); a resolver that special-cases `if county == "X"` is a confession the logic is patching an instance instead of modeling the mechanism — the reference resolver `_ward_map_per_county` keys on *observed behavior* (dominant resolved parent), so a county it has never seen is handled by the same logic as one it has. This law is *why* the rules below exist; when a jurisdiction bug recurs, the root cause is almost always this assumption made without a profile, not a code defect.
* **Single-resolver logic.** Never duplicate extraction/derivation (e.g. the jurisdiction hierarchy) **or infrastructure constants** (repo-relative paths, partition-key formats). Define one Python resolver/constant and reuse it across indexers, summaries, and JS-fed outputs — divergent copies are how the postal-city bug survived, and how `DATA_DIR`/`PARQUET_DIR`-equivalents ended up independently redefined across 30 files with a dozen different names (audited 2026-07-31; `local/context/handoffs/HANDOFF_DATA_DIR_CONSOLIDATION_AND_STATE_READINESS.md`) — including a live formatting inconsistency (`f'COUNTY_NUMBER={cnum}'` vs `f'COUNTY_NUMBER={int(cnum)}'`) between two "identical" copies. A path or partition-key constant needed by more than one script belongs in one shared module, imported — not retyped.
* **Parquet, partitioned by county**, for intermediate layers; GeoParquet for spatial. `COUNTY_NUMBER` is a *partition key*, not a column inside the parquet files — re-add it as a literal when reading partitions (the most common KeyError for new contributors).
* **Atomic writes:** `.parquet.tmp` → `.replace()`; never leave a partial cache. Enriched cache at `local/source/parquet_enriched/enriched_voters.parquet`; freshness = cache mtime vs `max(latest_raw_partition_mtime, classifier_src_mtime)`.
* **Parallelism:** `ThreadPoolExecutor(max_workers=8)`, not multiprocessing (shared address space, avoids WinError 1450). Any cross-county step (e.g. the city→county map) must run single-threaded *after* all 88 counties are written.
* **Provenance preserved** in parquet metadata or sidecar JSON: BoE timestamps, original headers, source URLs.
* **Loud failures over silent degradation.** No `try/except` as control flow (sole operator). Optional layers (LLM enrichment) may degrade gracefully; the core pipeline must not.

## 6. Coding Conventions
* **Path resolution.** Do not rely on CWD. Resolve the project root from the file: `Path(__file__).resolve().parent` at repo root, `Path(__file__).resolve().parent.parent` for scripts under `pipeline/` or `tools/<sub>/`. If the resulting path (or a partition-key format built from it) is needed by more than one script, it is a single-resolver constant per §5 — import it, do not re-derive it.
* **Encoding.** ASCII console strings (global rule — cp1252 default). Project-specific line endings: `pipeline/ohio_voter_pipeline.py` and `docs/assets/v2.js` are CRLF; `pipeline/voter_data_cleaner.py` and `jurisdictional_groupings.py` are LF (verified 2026-07-10 by byte check against committed HEAD). The repo has **no** `.gitattributes` normalization in effect (`git check-attr text eol` -> unspecified), so git preserves whatever a patch writes: always byte-check a file's actual endings before patching and write them back unchanged — do not trust this list blindly.
* **Data naming conventions (source-vs-derived visual contrast).** Four layers, so a reviewer instantly separates untouched state data from our engineering: **(1) Source columns** — verbatim as the provider emits them; SWVF and new streams (`electedofficials.csv`) arrive `ALL-CAPS`/`UPPER_SNAKE` (`CITY`, `COUNTY_ID`, `OFCDESC`); never rename. **(2) Derived/engineered columns** — `snake_case` (`birth_year`, `general_turnout_rate`); chosen for DuckDB/Postgres case-fold safety (unquoted `PascalCase` folds and collides) and PEP 8 cohesion. **(3) Transients** — `_leading_snake_case` (`_age_temp`); dropped before any parquet write. **(4) Display headers** — `Title Case With Spaces`; edge-only (frontend render / Excel export), never inside a Polars DataFrame. The convention governs column **names**, never string **values** — Generation values like `Silent/Greatest` are load-bearing filter keys (§4). Existing `PascalCase` temporals are legacy pending migration (§4); apply `snake_case` to all new derived columns from the start.

## 7. Testing and Quality Bar
* **Bounded data checks** before asserting state or data origin (global rule — `COUNT(*)`/`LIMIT`/`value_counts()`/mtime, results in a few hundred tokens; never guess provenance). Project corollary: verify a column **reaches** the function, not merely that it exists in the source — a targeted reader loading a column subset can pass a schema check and still raise downstream.
* **Error policy.** Log malformed rows to `local/working/errors/[county].log` and continue. Never halt on a parse error.
* `tools/admin/validate_jurisdiction_fields.py` is the data-validation gate; run it on every new SWVF drop.
* **`DATA_QUALITY.md` is the heterogeneity registry** — the single ledger of every known per-county deviation (§5's four levels: value / schema / format / provenance), keyed by `Stream` (jurisdiction is one stream; results, elected-officials follow). Its `<!-- auto:begin/end -->` block is machine-regenerated (`validate_jurisdiction_fields.py --ledger`); the manual section below it records the human decision + BoE contact. When a new mole appears, read this registry *first* — a known deviation gets a resolver that cites its row; a new one gets profiled and appended. Never open a second registry; drift between two ledgers is the exact disease §5 forbids.

## 9. Safe-Change Rules
* **File editing (Claude Code CLI / VSCode).** Use the Edit tool only for files ≤150 lines. The Edit tool and bash heredocs both truncate **silently** — a failed write looks identical to a success until parsing fails downstream. For larger files, write a Python patch script to `local/patches/` (`p.read_text()` / `p.write_text()`), then validate (`python -c "import ast; ast.parse(...)"` or `node --check`). Use `python` / `.venv\Scripts\python.exe` in Git Bash. For payloads >50 lines write via `Path.write_text(content)`; never `cat << 'EOF' >> file`. (Cowork inverts this rule — its FUSE mount makes patch scripts unusable; those host-specific instructions live in `local/context/cowork-instructions.md`, pasted into Cowork sessions, and are intentionally not carried here.)
* **Zero-trust security.** Never commit *personal* email or phone numbers (PII). Name, DOB, and address are public record. Published office contact for public officials — office email/phone/address/website (the `O*` columns in `electedofficials.csv`) — is civic data, **not** PII, and is committable; withhold only personal/home email and phone (the `H*` email/phone fields). Home address (`H*` address) is "public record" by the rule but bulk-republishing it is a policy call — default to dropping unless decided otherwise. `local/` stays entirely in `.gitignore`.
* **Verify input sources** before proposing a fix (global rule; see `~/.claude/CLAUDE.md`). Do not break a working contract to accommodate a muscle-memory typo.
* **Bulk-content push ban.** Never serialize `docs/data/` (~78k generated JSON files) through a token-metered transport — the GitHub MCP `push_files` or any similar tool that sends file *contents* as tokens. It bills the entire dataset as tokens and exhausted the account budget once. Batch changed *code* files into a single `push_files` call; regenerated `docs/data/` and binaries are pushed by the user via `git push` (§10).
* **Claude Code CLI / VSCode host-scanner avoidance** (the `\n#` multi-line `-c` flag, `cd`+redirection, the `| head` compound trap) is host-engine behavior and lives in the global `~/.claude/rules/cli-command-execution.md`. It does not fire in Cowork, so it is intentionally not duplicated here. This repo whitelists `awk`, `sed`, `xargs`, and `stat` in `.claude/settings.local.json`, so those need no avoidance workaround.

## 10. Specific Commands
**Committing works from the agent's tool shell and needs no auth — the agent may branch + commit directly.** **Pushing is HOST-dependent — ask which interface is running before assuming (global Git rule).** Do NOT default to "push is blocked / push is yours." `git push` authenticates fine from the VSCode/desktop extension; it fails only in a truly non-interactive shell (plain Claude Code CLI Bash, Cowork sandbox) with `Unable to persist credentials with the 'wincredman' credential store` / `could not read Username` (no TTY for Git Credential Manager). So at a push point: ask which interface I'm in, then if it can push, just try `git push`; only if it genuinely can't, hand it to the user, two ways:
* User runs it in a real terminal (PowerShell / VS Code):
```powershell
cd "D:\vibe\election-data"
git push -u origin <branch>
```
* Or the user types `! git push -u origin <branch>` in the prompt — the `!` prefix runs in their interactive session, where wincredman can authenticate.
* **Safe git search** (repo has ~78k generated files): `git log -S "term" --no-renames | head -n 20`; scope `grep` / `git grep` to a subdirectory, never repo root. One-time: `git config diff.renameLimit 10000`.
* **Stuck `.git/index.lock`** from a failed sandbox op: `Remove-Item ".git\index.lock" -Force`, then commit from PowerShell / VS Code.
